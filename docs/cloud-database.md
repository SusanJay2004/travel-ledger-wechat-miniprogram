# 云数据库模型与权限

## 权限原则

- `users`、`trips` 及后续协作集合全部禁止小程序客户端直接读写。
- 用户身份只能由云函数中的微信 `OPENID` 建立，客户端传入的用户 ID 不能作为鉴权依据。
- 所有写命令校验成员身份、资源状态和 `expectedVersion`；版本不一致返回 `VERSION_CONFLICT`。
- 金额只保存整数分，日期只保存 `YYYY-MM-DD` 字符串，事件时间保存 ISO 8601 UTC 字符串。

## `users`

- `_id` / `id`：内部稳定 ID。
- `openId`：微信环境内用户身份，只允许云端读取。
- `publicId`：10 位公开搜索 ID。
- `displayName`、`signature`、`avatarUrl`：用户资料。
- `homeTripCount`：首页行程的原子容量计数；创建、邀请加入、恢复、重开、归档和退出均与行程文档在同一云数据库事务中增减。
- `avatarUrl` 必须位于 `avatars/<当前内部用户ID>/`，并由云存储“创建者本人写入/删除”规则与云端路径校验共同保护，不能引用其他账号文件。
- `qrCodeFileId`、`qrSceneToken`：协作版个人小程序码文件和 20 位随机不透明场景令牌；二维码不包含公开 ID、内部 ID 或 `OpenID`，云端解析后只返回可申请好友的公开资料。
- `status`、`version`、`createdAt`、`updatedAt`：生命周期与乐观并发字段。资料、二维码和注销均按 `version` 条件更新，避免并发请求覆盖注销状态。
- `pendingFileDeletionIds`：换头像或注销时与资料版本原子记录的待删除云文件；API 立即尝试清理，失败由每日维护重试，不能只依赖客户端删除旧文件。
- `pendingAvatarFileId`、`pendingAvatarReviewId`、`pendingAvatarExpiresAt`：2.0 异步头像审核候选、未公开的微信 `trace_id` 与 35 分钟兜底期限。旧头像在回调明确 `pass` 前继续生效；风险/超时候选进入持久化删除清单。`pendingAvatarReviewId` 使用唯一稀疏索引，`pendingAvatarExpiresAt` 使用普通索引。

唯一索引：`openId`、`publicId`、稀疏 `qrSceneToken`；普通索引：`_id + version`、`status`。

首页 100 条上限不能通过“先查询数量、再写行程”实现，因为并发请求会同时通过。服务端以 `users.homeTripCount` 为事务内计数器：事务读取用户和行程版本，校验增量后同时写入；账号资料更新也递增同一用户版本，避免覆盖计数。部署到已有数据的环境前必须先按 `members.viewState == home` 回填并核对计数；当前首次开发环境无历史生产数据，可从 0 初始化。

## `trips`

- `_id` / `id`、`name`、`status`。
- `memberIds`：用于成员过滤的内部 ID 数组。
- `members`：成员显示名快照和每用户 `home|archived|detached` 状态。
- `dates`：有序日历日期。
- `bills`：账单、参与份额、付款明细、校验码和软删除字段。
- 参与人与付款人的显示名由云端根据行程成员快照重建；客户端提交的显示名不作为权威数据。
- `totalCents`、`invalidBillCount`：列表派生摘要。
- `version`：所有写入的乐观并发版本。
- `ledgerRevision`：影响分账结果的账本版本。
- 操作者、创建/修改/完结时间字段。

普通索引：`memberIds`、`version`。

## 协作集合

协作模式还使用以下禁止客户端直接读写的集合：

- `friend_requests`：好友申请及 30 天有效期。
- `friendships`：排序后的双用户 ID 数组。
- `blocks`：单向拉黑关系。
- `notifications`：用户自己的应用内通知。
- `trip_invitations`：行程邀请及 7 天有效期。
- `sync_events`：每个成员自己的实时同步信号，携带由云端写入的 `ownerOpenId`。
- `audit_logs`：行程变更操作审计，仅云端可读写。
- `idempotency_records`：写命令的请求去重、完成或失败结果，保留 24 小时。
- `rate_limit_records`：按哈希身份、操作范围和时间窗记录的限流令牌，不保存明文 `OpenID`。

需要为各集合的用户 ID、状态和到期时间组合建立查询索引。生产云函数默认 `solo`；只有平台发布门禁通过后才设置环境变量 `PRODUCT_MODE=collaboration`。

`friend_requests.pendingKey` 与 `trip_invitations.pendingKey` 使用唯一稀疏索引，并只把活动哈希键用于待处理记录。它们分别按双方账号、以及行程与被邀请人生成不可逆哈希键；接受或拒绝时移除，到期重发时先以状态条件把旧键替换为该记录专属的已解决标记。这样不同设备使用不同 `requestId` 并发提交时也只会保留一个待处理入口，同时不会让刚过期、尚未来得及由维护任务清理的记录阻止重发。

`sync_events` 是唯一需要客户端读取的协作集合，安全规则必须同时满足：

```json
{
  "read": "auth.openid == doc.ownerOpenId",
  "write": false
}
```

客户端监听时必须带 `userId + tripId` 精确条件；其他协作集合继续保持客户端不可读写。

所有写命令都必须携带 8–80 位 `requestId`。云端以 `SHA-256(OpenID + requestId)`
作为幂等记录主键；同一请求的网络重试复用原标识并返回首次结果。若业务可能已提交但结果记录写入失败，
记录保持 `processing`，服务端拒绝重放并要求客户端刷新权威数据，不能删除标记后重复执行。

审计和同步投影使用“行程 ID + 版本 + 动作 + 用户”的确定性文档 ID，重复发布不会生成重复记录。
投影失败记录结构化错误但不把已经提交的账本写入伪装成失败；待投影事件与账本原子写入 `Trip.projectionOutbox`，每日维护任务用确定性 ID 重放审计、用户同步信号和生命周期通知。进入多人灰度前必须在开发云环境主动制造一次投影失败并演练修复。

接受行程邀请时不只检查 7 天有效期，还会重新验证邀请人仍是当前成员、双方仍为好友且不存在双向拉黑，防止旧授权状态被继续使用。

归档是每位成员独立的视图状态；30 天到期后服务端拒绝恢复并不再返回到期记录。用户主动清空时仅将自己的
`viewState` 改为 `detached`，不会删除其他成员仍保留的共享行程。“清空”由幂等云命令每批最多处理 20 条，前端按产品 100 条上限至多执行 5 批，避免异常响应导致无界重试或逐条请求触发限流；版本冲突项保留并重新拉取。
定时清理任务负责删除所有成员都已脱离的孤儿数据。

账号注销先把用户标记为 `deleting` 并持久化 `pendingFileDeletionIds`，匿名化全部历史账务快照并脱离行程，再清理好友、拉黑、邀请、通知、
同步事件，最后解绑 `OpenID` 并标记 `deleted`。API 立即尝试删除云存储个人文件；失败时每日维护继续按清单重试，成功后才清空标记。
历史金额和内部成员 ID 保留以维持共享账务守恒；再次进入会创建全新账号，不能恢复旧行程。中途失败可重试，已经匿名化的行程不会重复改写。
关联社交数据按每批 20 条逐文档循环清理到空，避免依赖云数据库条件删除的单次后端上限；不同关系方向分别处理，且不删除其他用户之间的数据。

## 生产前迁移方向

当前单人 MVP 将最多 100 条账单内嵌在行程文档中，以便事务式原型开发。进入多人灰度前必须执行容量压测；若接近云数据库单文档限制，则将账单迁移至独立 `bills` 集合，并保留 `Trip` 摘要与版本字段。迁移必须提供双读校验、备份和回滚脚本，不能直接修改生产数据。

为防止反复软删除/新增令内嵌数组无限增长，服务端最多保留 500 条“有效账单 + 30 天内软删除账单”；有效账单仍严格限制为 100 条，软删除记录不占这 100 条名额。新增账单时会先清理已超过恢复期的记录；若 500 条全部仍在恢复期内，则暂时阻止新增并提示等待到期。自动化容量测试以 20 人、100 条有效账单、400 条近期软删除账单和最大字段构造保守样例，进入多人灰度前还必须在真实云数据库写入并读取该样例。
