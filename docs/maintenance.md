# 定时维护与数据保留

`cloudfunctions/maintenance` 是只由云开发定时触发器调用的维护函数，不向小程序客户端暴露。

入口明确要求 `getWXContext().SOURCE === 'wx_trigger'`；来自小程序、开发者工具、HTTP、其他云函数或缺少来源字段的调用全部拒绝。

建议在开发、体验和生产环境分别配置每天凌晨执行一次，例如北京时间 03:30。部署后必须检查函数日志中的 `maintenance-complete` 摘要并设置失败告警。

任务会分批处理并执行：

- 删除已过期的幂等记录和限流令牌。
- 删除已过期的好友申请和行程邀请；应用内通知仍作为已发生事件保留。
- 删除超过 7 天的实时同步信号；客户端重进页面会重新拉取权威数据。
- 删除超过 180 天的操作审计；删除前关键事故证据按合规流程另行留档。
- 重试删除资料换头像和已注销账号留下的头像/个人小程序码；资料更新先原子记录旧文件清单，文件删除成功并通过用户版本条件后才清空待清理标记。
- 重放行程文档 `projectionOutbox` 中尚未成功生成的审计、同步信号和生命周期通知；使用确定性 ID 保证重复运行不产生重复记录。
- 把超过 30 天恢复期的个人归档状态转为 `detached`。
- 从行程文档中永久移除超过 30 天的软删除账单。
- 当所有成员都已 `detached` 时，删除孤儿行程及其审计、同步、邀请和通知关系。

孤儿行程会先清理关联集合，全部成功后才条件删除行程主文档；若任一关联集合失败，主文档保留到下一次任务继续重试，避免半途失败后失去清理入口。

行程更新和删除都带 `version` 条件。若用户同时编辑导致冲突，维护任务跳过该行程并在下一日重试，不覆盖用户写入。

行程和待清理注销用户按 `_id` 升序游标逐页处理，不用 `skip`、不一次加载全表；运行途中新增且排在当前游标之前的记录会在下一次定时任务处理，不会永久遗漏。

每次共享写入会先把待投影事件和账本变更原子保存，再尝试即时投影；只有审计、所有成员同步信号和对应系统通知全部成功后才移除事件。积压最多保留 1000 条，超过后临时冻结该行程的新写入并告警，避免行程文档无限增长。维护摘要中的 `projectionsRepaired` 和 `projectionFailures` 必须纳入监控；任何失败都要核对缺失用户、集合权限和配额。

## 上线演练

1. 在开发环境创建未来和过期两组虚构数据。
2. 手动触发维护函数，核对摘要、行程金额、账单数量、归档状态和关联集合。
3. 再次触发，确认结果幂等且无额外删除。
4. 与一名用户同时修改同一行程，确认维护函数记录 `conflictsSkipped` 且未覆盖修改。
5. 生产定时触发器启用后设置函数失败、执行时长和数据库用量告警。
